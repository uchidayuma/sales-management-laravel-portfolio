# テストケース作成スキル

GitHub Issueとソースコードを一次情報として、7人の意地悪なQAペルソナの視点でテストケースを作り、
`qa/cases/` にMarkdownとして保存する。**テスト設計のみ行い、コードは一切変更しない。**

引数 `$ARGUMENTS` はGitHub Issue番号（例: `12`）。

## 前提: 7人のQAペルソナ

「動いているはず」を信用せず、各ペルソナの視点で最低1ケースずつ観点を残す。

| # | ペルソナ | 疑う点 |
| --- | --- | --- |
| P1 | 新人ユーザー | 説明を読まず直感で操作。誤クリック・空送信・連打で壊れないか |
| P2 | ベテラン現場担当 | キーボードで高速・大量入力。Tab遷移／ショートカット／IME変換中のEnter |
| P3 | 悪意ある操作者 | 境界値・不正値・権限外・二重送信。バリデーションや排他制御が効くか |
| P4 | データ整合性監査役 | 画面を信用せず裏のDB/APIレスポンスを直接確認。CRUDの整合性 |
| P5 | 移行担当者 | 既存データ（旧仕様の値）を投入した場合の欠損・異形式・文字コード |
| P6 | 回帰デグレ番人 | 「今まで動いていた何か」が壊れていないか。周辺機能やリロード後の挙動 |
| P7 | 仕様懐疑者 | 「実装＝正しい仕様」を信用しない。一次情報（Issue）と挙動を突合 |

## STEP 1: Issueの要件を確認する

```
gh issue view $ARGUMENTS --json title,body,comments,labels,url
```

- 本文・コメントを読み、受け入れ条件を日本語のまま整理する（意訳・要約しすぎない）。
- 曖昧な表現や、テスト可否を判断できない要件があれば、そのままリストアップしておく（STEP4で使う）。

## STEP 2: 関連実装を調査する

- `routes/web.php` と `routes/api.php` から、Issueに対応するルートを特定する。
- 該当するControllerを `app/Http/Controllers/` から読み、バリデーションは `app/Http/Requests/` で確認する。
- ビジネスロジックが `app/Services/` にあればそちらも読む。
- Model（`app/Models/`）のリレーション・スコープ・$fillableを確認する。
- Bladeテンプレート（`resources/views/`）で画面のフォーム構造を確認する。
- 確認できたファイルは `file:line` 形式で控えておく（STEP4のTest Basis列で使う）。

## STEP 3: 根拠のないケースを出さないためのルール

- コードを確認できていない箇所は、推測で埋めず「※要静的解析（未実施）」と正直に書く。
- Test Basis（一次情報）列には、必ずIssue番号・`file:line` のいずれかを引く。独自の推測だけで期待結果を作らない。

## STEP 4: テストケースをMarkdownで生成する

文字コードはUTF-8。ファイル冒頭にタイトル・所見サマリー・ペルソナ内訳、続けてテストケース1件につき `###` 見出し1つを立てる形式で固定する。

所見サマリーは「テストケースを並べただけでは結論が伝わらない」を防ぐためのセクション。
テストケースを作る過程で「これは実装が怪しい／デグレの疑いがある／ドキュメントが無い」等の気づきが出たら、
期待結果や備考に書いて終わりにせず、必ずここに1行で拾い上げる。

```markdown
# テストケース: Issue #<issue番号> <Issueタイトル>

## 所見サマリー

<全体の結論を1〜2文。>

| # | 指摘事項 | 種別 | 推奨アクション | 関連テストケース |
| --- | --- | --- | --- | --- |
| 1 | <一言で「何が問題か」> | バグ疑い／仕様懸念／回帰リスク | <何を直す／誰に確認するか> | TEST-<issue番号>-00N |

## ペルソナ内訳

| ペルソナ | 件数 |
| --- | --- |
| P1 新人ユーザー | n件 |
| P2 ベテラン現場担当 | n件 |
| P3 悪意ある操作者 | n件 |
| P4 データ整合性監査役 | n件 |
| P5 移行担当者 | n件 |
| P6 回帰デグレ番人 | n件 |
| P7 仕様懐疑者 | n件 |

---

### TEST-<issue番号>-001: <テストタイトル>

- **ペルソナ**: P1 新人ユーザー
- **優先度**: 高／中／低

**前提条件**

<前提条件を1〜2文で>

**操作手順**

1. <手順1>
2. <手順2>

**期待結果**

<期待結果>

- **Test Basis**: `file:line` / Issue #<issue番号> のコメント
- **備考**: 確認が取れていない事項があれば明記。無ければ省略可
```

- ID: `TEST-<issue番号>-001` のように連番。
- P1〜P7それぞれ最低1件は含める。
- 操作手順は必ず番号付きリスト。
- 備考が無いテストケースでは備考行ごと省略。

STEP1で洗い出した曖昧な要件は、ファイル末尾に `## テスト不可・要確認事項` 見出しを立てて明示する。

## STEP 5: 保存とサマリ提示

- `qa/cases/<issue番号>-<機能を表す短い英語スラッグ>.md` に保存する。
- 保存後、**まず所見サマリーの内容をチャット本文に転記する**。Markdownファイルを開かなくても結論がわかることを優先。
- そのうえで保存先パス・件数・ペルソナ内訳を提示。
- **Issueへのコメント投稿は行わない。** ユーザーから明示的に指示があった場合のみ投稿する。
